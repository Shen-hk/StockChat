# 35-项目优化设计评审_v1.0

> 产出方：软件开发团队（架构师高见远评审，主理人齐活林汇编）
> 日期：2026-09-08
> 范围：全项目现状体检 + 优化路线图（用户未指定方向，按全面体检处理）
> 证据基准：当日工作区代码，行号以当日文件为准

## 一、总体评价

项目分层意图清晰（page/chat/cards/composer/protocol/data/glass 各司其职），纯逻辑下沉 commonTest 的做法（16 个测试文件覆盖 store/parser/reducer/rules，含 ArchitectureBoundariesTest）和 R1-R5 规范的文档化程度在 Demo 项目中属于优秀水平，历史 10 条坑多数已有个案修复并附带高质量注释。

当前最大的结构性风险有四：

1. **ChatPage.kt 已成 5089 行巨石**（约 90 个状态字段 + 110+ 方法，聊天渲染/输入栏状态机/语音/灵动岛/对比/SideSheet/抽屉/欢迎页/滚动跟随/卡片重试十几种职责同居一个 Pager 作用域）；
2. **依赖图按 pager 各自构建，且 MarketPage 同页持双图**，导致 QuoteRepository 等数据层多实例、缓存与请求重复；
3. **跨页状态同步（自选股）无变更通知机制**，靠手动 reload 兜底且只覆盖部分页面；
4. **R1-R5 防护仍停留在"注释约定 + 个案封装"**，双态机、版本守卫等模式在 ChatPage 内重复 6+ 处而未抽成通用组件。

另外鸿蒙端构建脚本与主构建脚本已明显漂移，四端目标实际处于"3.5 端"状态。

## 二、问题清单

### P0-1【架构】ChatPage 上帝文件，状态机约定无法编译期保证

- **证据**：`shared/src/commonMain/kotlin/com/kuikly/stockchat/page/ChatPage.kt` 共 5089 行；仅 L191–L433 就声明约 90 个字段（含 ~60 个 observable）；grep 统计 110+ 个 private fun。典型脆弱点：`composerExpanded` 共 6 个写入点（L1993、L2093、L2185、L2319、L2324、L2330），但 `scheduleComposerChromePresentation` 只有 4 处成对调用（L1997、L2096、L2187、L2328）——`restoreAfterVoiceSession()` 的 `composerExpanded = true` 分支（L2330）依赖"presented 本就是 true"这一隐式不变量，注释只解释了 false 路径。任何后续改动都可能复现"图标永远停在 opacity 0"（历史坑 7）。
- **建议**：按 feature-state 拆控制器：ComposerController（折叠/展开/chrome 翻转/focus 恢复收敛为 expand()/collapse() 两个入口）、IslandController、VoiceSessionController、ChatScrollFollowController、CompareController；ChatPage 只剩装配 + body。目标单文件 <1000 行，`composerExpanded` 写入点从 6 收敛到 1–2。

### P0-2【数据层/依赖图】per-pager 多实例 + 同页双依赖图

- **证据**：`MarketDependencies.forPager()`（data/MarketDependencies.kt:26–48）每次调用新建 QuoteRepository/WatchlistStore/EastMoneyInsightProvider 全套；`ChatDependencies.forPager()`（chat/ChatDependencies.kt:25–37）内部又建一个 MarketDependencies；而 `MarketPage.kt:77` 与 `MarketPage.kt:114` **同时**持有 `dependencies`（MarketDependencies）和 `aiDependencies`（ChatDependencies）——同一 pager 存在 3 个 QuoteRepository 实例。QuoteRepository 的内存缓存（QuoteRepository.kt:21–24 snapshots/timelines/kLines）互不相通，且每个实例 init 时经 `SharedPreferencesQuoteCacheStore` 全量 restore（QuoteRepository.kt:141–151）。
- **后果**：同一 symbol 在不同页各自请求与缓存，跨页数字可能不一致；网络与解析重复；内存浪费。
- **建议**：数据层实例提升为进程级单例（Kuikly module 级注册表或 lazy AppScope），per-pager 只留 UI 态与 ViewRef。

### P1-1【状态管理】跨页状态同步无通知机制，reload 覆盖不全

- **证据**：WatchlistStore 纯 storage 读写（data/WatchlistStore.kt:50–156），无变更广播；每次 `list()` 全量 JSON 解析（WatchlistStore.kt:158–189）。全仓只有 ChatPage（ChatPage.kt:482）和 StockDetailPage（StockDetailPage.kt:193）实现 `pageDidAppear`；WatchlistPage 仅在 created（WatchlistPage.kt:166）及本页操作后 reload（WatchlistPage.kt:1411）。从聊天/详情页改动自选后返回自选页，UI 是否新鲜取决于页面栈是否重建——潜在陈旧态。
- **建议**：给共享 store 加轻量版本号/监听器（Kuikly observable 或手动 listener registry），页面 pageDidAppear 时按版本号决定是否 reload；滚动路径上的 `list()` 改读缓存快照。

### P1-2【R1-R5 落地】通用模式未组件化，双态机/版本守卫大量复制

- **证据**：mounted→presented 双态机在 ChatPage 至少 6 组重复：drawer（L249–251）、sheet（L373–375）、messageAction（L226–227）、chatBackToTop（L385–386）、welcomeEntrance（L409–410）、composerChrome（L430）；`xxxVersion` 版本守卫字段 12+ 处（L220、L251、L264、L284、L371、L382、L387、L402、L413、L431…）；Timer 字段 7 个（chatFollowLoop L203、voiceClockTimer L356、welcomeKeywordTimer L403、welcomeCursorTimer L404、welcomeEntranceTimer L415、welcomeEntranceSafetyTimer L418、composerRimFlowTimer L425），生命周期全靠手工 stop，页面销毁无统一取消清单。
- **建议**：抽 `TwoPhasePresence`（封装 mounted/presented/version/timer 三件套）与 `VersionedTimer`（版本守卫 + cancel），在全部落点替换；AGENTS.md 相应规则改为"必须使用该组件"。

### P1-3【多端一致性】双构建脚本漂移，鸿蒙端疑似失养

- **证据**：`shared/build.ohos.gradle.kts` 声明 `ohosArm64` 目标（L39–44），但 shared/src 无 ohosMain source set；4 个 expect 函数（PlatformHttpClient/PlatformMotion/QuoteClock/PlatformNavigation，见 PlatformHttpClient.kt:6）仅有 android/ios/js actual；ohos 版 commonMain 依赖（build.ohos.gradle.kts:47–51）缺 `ktor-client-core` 与 `chartkit`，而 common 代码直接 import `io.ktor.client.HttpClient`（PlatformHttpClient.kt:3）与 chartkit——按该脚本鸿蒙目标无法编译。KuiklyMarkdown 版本还钉在 ohos 专属旧版（1.0.6-2.0.21-ohos vs 主脚本 1.0.6-2.1.21）。
- **建议**：要么补齐 ohosMain actual + 依赖并纳入 CI 编译门禁，要么在 README/docs 明确声明鸿蒙为实验态、从"目标四端"范围中暂时摘除，避免团队按四端心智做设计。

### P1-4【数据层健壮性】网络层无在途合并/连接复用

- **证据**：`DeepSeekAiProvider` 每次实例化新建 HttpClient 且从不 close（AiProvider.kt:34）；`QuoteRepository.load()` 每次无条件并发刷新 3 个 K 线 interval + 1 个 timeline（QuoteRepository.kt:40–55），TTL 内无去重；`snapshot()` 与 `load()` 无在途请求合并（去重只存在于 ChatPage 的 `requestedSymbols` L399，页级 patch 而非仓库层机制）。
- **建议**：QuoteRepository 增加在途 Future/合并 + 按 interval 惰性拉取；HttpClient 进程级单例复用。

### P2-1【工程卫生】模板残留与调试产物

- **证据**：RouterPage.kt 仍是 Kuikly 模板调试路由（RouterPage.kt:16–231，"输入pageName"跳转 + ImageAdapter 基准测试入口），配套 ImageAdapterBenchmarks.kt 348 行；仓库根目录 40+ 调试截图/脚本（dbg-*.png、wb-*.png、patch_longpress.py、swipe-exp.sh 等）未 gitignore。
- **建议**：调试路由隔离到独立 pageName 或删除；调试产物清理 + .gitignore。

### P2-2【架构】巨型 DSL 函数

- **证据**：AppChrome.kt 1689 行，其中 `StockIsland` 单函数约 750 行（AppChrome.kt:312–1066），股票岛与术语岛共用一条手势/形变管线挤在一个函数里。
- **建议**：按"壳层/手势/行情内容层/术语内容层"拆 4 个函数或子组件。

### P2-3【重复代码】卡片类型元数据分散

- **证据**：卡片类型清单至少 3 处独立维护：SYSTEM_PROMPT（AiProvider.kt:156）、ChatViewModel.cardRetryPayloadExample（ChatViewModel.kt:303–308）、MockAiProvider 各 answer 的硬编码卡片块（AiProvider.kt:197–278）。
- **建议**：CardRegistry 增加 per-type 的 payload 示例/描述元数据，三处改为单源引用。

### P2-4【可测试性】ChatViewModel 无测试；存储层手写 JSON

- **证据**：commonTest 16 个文件中无 ChatViewModel 相关用例（send/stop/retry/会话切换语义未覆盖）；5 个 store（WatchlistStore/ChatSessionStore/AlertStore/GlossaryStore/RiskSnapshotStore）各自手写 JSONArray 序列化 + optString 兼容，而已引入 kotlinx-serialization（build.gradle.kts:50）却未用于存储层；ChatSessionStore 把 30 会话 × 40 条消息序列化进单个 SharedPreferences key（ChatSessionStore.kt:176–183）。
- **建议**：存储层迁 kotlinx-serialization + 抽 StoreBase；ChatViewModel 以 fake AiProvider/QuoteRepository 补齐核心语义测试；会话存储中期改文件/分 key。

## 四、共享知识（建议沉淀进 AGENTS.md / 组件）

1. **双态机组件化**：新浮层/入场动效一律使用 TwoPhasePresence，禁止手写 mounted/presented/version 三字段组（当前 ChatPage 6 组重复即反面教材）。
2. **composerExpanded 配对规则收编**：散点规则（历史坑 7/9）在 ComposerController 落地后从 AGENTS.md 降级为一条"只能通过 expand()/collapse() 修改折叠态"。
3. **依赖图规则**：跨页共享的 store/repository 必须进程级单例；per-pager 只允许 UI 态与 ref；MarketPage 双图（L77/L114）为违规样板。
4. **Timer 规范**：一切定时回调必须版本守卫 + onDestroy 显式 cancel；新代码用 VersionedTimer，版本号普通字段不可在回调中读 observable（现有正确实践固化）。
5. **历史坑 10 条处置结论**：坑 2/3/4 已组件级收口（AtmosphereBackdrop 唯一入口、Border 全参写法已成惯例）；坑 5/6/8 属个案修复有注释但未抽象，建议随 B1/B2 一并组件化；坑 7/9 按第 1/2 条收编。
6. **卡片协议单源**：新增卡片类型只改 CardRegistry（类型名、payload 示例、渲染器、Mock 回答四处合一）。
7. **存储迁移规范**：新增字段必须 optString 兼容缺省（现状正确），但新 store 一律用 kotlinx-serialization + StoreBase。
