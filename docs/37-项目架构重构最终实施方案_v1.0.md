# StockChat 项目架构重构最终实施方案

> 版本：v1.0 ｜ 制定：2026-09-09 ｜ 本轮可用重构窗口：1 个工作日
>
> 本文整合既有《StockChat 项目架构实施计划》与当前代码审计结果。它只定义架构和实施边界；不把文档中的竞赛判断、五日排期或其他任务当作本轮的隐含开发指令。

## 1. 最终决策

本轮不尝试在一天内把 `ChatPage.kt` “拆完”。当前页面有 5,631 行、83 个响应式状态、48 处延迟调度与 227 个函数；一次同时迁移语音、附件、实体拖拽、抽屉、灵动岛，会把 Kuikly 的响应式依赖、动画注册滞后一帧与原生手势命中问题叠加，无法在一天内可靠验收。

一天内的正确交付是一个**完整、可复制、可回滚的纵向架构试点**：把聊天欢迎区从 Page 中完整拆到 Page / Component / State / Data 四层，并建立可阻止架构回退的规则、测试与迁移模板。其余高风险状态机保留原位，后续按模板逐个迁移。

这能同时满足三件事：

1. 真实降低 `ChatPage` 的职责，而不是仅移动函数；
2. 保持现有交互、时序和页面路由不变；
3. 给后续聊天、详情、自选、市场页提供经真机验证的拆分范式。

`Task1` 可继续复用已有行情、卡片和详情能力，但不与本次重构绑定；新入口页与架构重构必须是独立提交、独立回滚的工作流。

## 2. 目标架构

工程按“功能纵切，功能内四层分离”组织。`foundation` 和顶层 `component` 是跨功能共享基座，不是第五个业务层。

```text
feature/
  chat/
    page/          ChatPage.kt
    component/     ChatWelcomeSection.kt, ChatComposer.kt, SessionDrawer.kt
    state/         ChatWelcomeState.kt, ChatWelcomeCoordinator.kt,
                   ChatIntent.kt, ChatEffect.kt
    data/          WelcomeStarterStore.kt, ChatSessionRepository.kt
  detail/          page / component / state / data
  market/          page / component / state / data
  watchlist/       page / component / state / data
  risk/            page / component / state / data

foundation/
  page/            BasePager, page 生命周期适配
  motion/          PagerTaskScope, 任务取消与版本守卫
  platform/        BridgePort, NavigationPort, StoragePort
  design/          Theme, Token, MotionSpec, Icon

component/          仅放已被至少两个 feature 稳定复用的组件
  chrome/           AppBar, GlassSurface
  overlay/          ModalSheet, UndoBar
  feedback/         Loading, Empty, Error, SourceStamp
  card/             CardShell 与卡片通用外壳
```

### 2.1 四层责任与依赖方向

```text
Page ──组装/生命周期──> Component
  │                         │
  └──── Intent / 回调 ────> State ───> Data port / repository
                                  │
                                  └──> Effect ──> Page platform adapter
```

| 层 | 责任 | 禁止项 |
|---|---|---|
| `page` | 路由参数、生命周期、依赖装配、处理平台 Effect | 直接请求 Provider、持有业务定时器、堆积交互字段 |
| `component` | 接收 State 访问器和 Action 回调，完成 UI 渲染 | `acquireModule`、`PagerKeyValueStorage`、Repository/Provider/Store 调用、跨组件时序决策 |
| `state` | UI 状态、Intent、Effect、页面级协调器和时序状态机 | 构建 Kuikly View、持有具体原生 Bridge |
| `data` | 不可变模型、缓存、持久化、网络、Repository / Provider | Kuikly View、页面 observable、导航或 Toast |

组件可依赖 `data/model` 中的只读模型，但不能依赖数据源。所有跨端业务数据必须在 `commonMain`；各端实现只在 `androidMain`、`iosMain`、`jsMain`。

## 3. 本轮试点：聊天欢迎区

选择欢迎区而不是 Voice、Drawer 或 Island，原因是它能覆盖存储、定时、R4 两帧入场、页面可见性与 UI 复用，却不涉及录音权限、输入框焦点、帧级跟手或跨页面形变。

目标拆分如下：

```text
feature/chat/
  data/WelcomeStarterStore.kt
    - 读取与写入已使用的 starter kind
    - 接收 StoragePort；不认识 Pager

  state/ChatWelcomeState.kt
    - rotatingKeyword, cursorVisible, entranceVisible
    - marketTabSelected, stopped, version

  state/ChatWelcomeCoordinator.kt
    - onCreated / onAppear / onDisappear / onWelcomeMounted / onNewSession
    - 唯一拥有欢迎区 Timer、版本号、降级动效策略
    - 只 dispatch State/Effect，不读写 ViewRef

  component/ChatWelcomeSection.kt
    - 从现有 WelcomeSection 迁入
    - 接收状态访问器和 onChoose/onOpenMarket 回调
    - observable 仅在 attr/event/vif/vbind 内读取

  page/ChatPage.kt
    - 创建 coordinator，转发生命周期和用户 Intent
    - 不再持有 welcomeStorage、welcomeKeywordTimer、welcomeEntranceTimer 等字段
```

迁移时必须原样保留现有的“mounted → 下一帧 presented → 安全兜底”逻辑。不可为了整洁把两个定时器折叠成一个，或在预状态注册 0 时长动画；这会违反项目 R4/R5 并导致欢迎内容跳变或透明卡片滞留。

## 4. 时序不可变规则

1. 一个视觉时序只能有一个 Coordinator 所有者；回调只能通过 Intent 改状态。
2. 延迟任务统一由 `PagerTaskScope` 或等价封装登记，并按 feature 的 `version`、页面可见性和销毁状态校验。
3. `pageDidDisappear` 与 `pageWillDestroy` 必须取消任务、递增版本；过期回调必须 no-op。
4. 组件不得在普通 `body()` 或子 builder 中读取 observable 快照；必须在 `attr`、`event`、`vif`、`vfor` 或 `vbind` 内读。
5. 动画 driver 必须是该 `attr` 最后读取的 observable，`animate()` 为最后一条状态相关语句；每次循环预注册下一次变化要播放的动画。
6. 外部线程、网络、原生回调不能直写 UI observable；先切回页面调度器并经过版本校验。

## 5. 一天执行排期与止损线

| 时段 | 交付 | 退出条件 |
|---|---|---|
| 0–1 小时 | 记录当前 Git diff、状态字段地图、Android/H5 关键路径截图与操作清单 | 工作区已有未提交改动必须与本轮改动隔离；否则只做文档和测试，不搬代码 |
| 1–2 小时 | 建立 package 依赖规则、欢迎区状态机测试、假时钟/假存储测试桩 | 现有单测与编译基线未稳定，不进入迁移 |
| 2–5 小时 | 完成欢迎区 Data / State / Component / Page 纵向迁移 | 每完成一层均编译；不改变 UI 文案、动画值与路由 |
| 5–6 小时 | Android 与 H5 回归：新会话、历史会话、切后台返回、降低动态效果、快速重复开关 | 任一路径异常，回退该试点 commit，不继续扩大范围 |
| 6–7 小时 | 清理跨层反向依赖：先处理 `SourceStamp` 等纯展示项；补架构检查 | 不触及 Drawer、Island、Entity drag、Voice、Composer focus |
| 7–8 小时 | 全量单测、Android/H5 编译、变更说明、独立提交 | 不以“再拆一个状态机”填充剩余时间 |

一天结束时的成功标准不是行数指标，而是：欢迎区完整走过四层；`ChatPage` 不再拥有其存储、定时与展示状态；异常回调可被测试证明不会更新已离开的页面；在 Android/H5 上行为与迁移前一致。

## 6. 后续迁移队列

在试点验收后，按风险而非视觉位置迁移，每个对象单独 commit、单独真机验证：

1. `CardSheetState`：挂载/呈现/层级/拖拽收敛；
2. `ChatScrollState`：流式贴底、回到顶部、内容高度；
3. `ComposerAttachmentState` 与 `MediaSheetState`：媒体回调必须经 Platform Effect；
4. `EntityDragState`：先保留现有手势与渲染函数，后移动状态所有权；
5. `DrawerGestureController`：原子 `phase + offsetX`、snap 与 fling 保持不变；
6. `IslandGestureController`：最后迁移，覆盖 IDLE / DRAGGING / RETURNING / CLOSING / OPENING_DETAIL 全部状态。

Voice 不列为“低风险练手项”：它同时关联录音桥、Timer、振幅和 Composer 焦点恢复，实际风险高于欢迎区、Sheet 和纯展示抽取。

详情、市场、自选、风险页不在本轮改动。待 Chat 试点成功后复制目录、规则与测试模板，再逐页收敛。

## 7. 共享组件孵化规则

- 已有至少两个稳定使用方才进入顶层 `component/`；否则留在 feature 内。
- `CardSheet`、`GlassSurface`、`AppBar`、`UndoBar`、`SourceStamp` 可成为共享候选。
- `DetailTimelineChart`、风险天空图、聊天灵动岛、详情业务卡片仍属于 feature 组件。
- `AppChrome` 需要拆成通用玻璃/导航基元与 Chat 专属 QuoteIsland、SessionDrawer；不能继续作为依赖聊天、术语、行情与图表的大型“通用”文件。

## 8. 命名、注释和质量门禁

| 类型 | 命名 |
|---|---|
| 页面 | `ChatPage`、`StockDetailPage` |
| 组件 | `ChatComposer`、`QuoteIsland`、`DetailHero` |
| 状态与事件 | `ChatWelcomeState`、`ChatIntent`、`ChatEffect` |
| 时序协调 | `ChatWelcomeCoordinator`、`DrawerGestureController` |
| 数据 | `QuoteRepository`、`QuoteDataSource`、`WelcomeStarterStore` |

禁止新增 `Common`、`Helper`、`Manager`、`Utils` 这类无边界命名。注释只说明时序不变量、平台差异、为什么不能合并或重排，不重复代码表意。

CI/本地质量门禁应覆盖：

1. `data` 不导入 `page`、`component` 或 Kuikly View；
2. `component` 不导入 Repository、Provider、Store、Bridge；
3. `page` 不直接导入业务 Provider；
4. 每个 Coordinator 有 fake scheduler 的时序单测；
5. 每个迁移 commit 运行 common test、Android 编译、JS 编译，并在 Android/H5 走对应人工交互清单。

## 9. 明确不做

- 不做 Redux、全局 Store 或引入新框架；现有 page-scoped dependencies 继续保留。
- 不在第一天拆 Gradle/KMP 模块；先以包规则验证边界，稳定后再单独做模块化技术预研。
- 不在同一 commit 迁移两个高风险手势状态机。
- 不混入 Task1 新页面、硬编码修复、仓库清理等其他目标；这些各自独立提交。
- 不修改当前工作区既有未提交改动，除非先明确它们的基线归属。

## 10. 交付物

本轮完成后应有：

1. 本文档与 Chat 状态字段地图；
2. 一个完整的欢迎区四层纵向切片；
3. 可执行的跨层依赖检查与欢迎区状态机测试；
4. Android/H5 回归证据；
5. 至少一个可独立回滚的重构 commit 和一份迁移说明。

后续开发可以把这套模板复制到每个 feature，而无需再次从 `ChatPage` 大文件中临时发明架构。

## 11. 重点组件工程模块化

目录分层不足以约束依赖；对高复用、高复杂度、可独立测试和可独立演进的能力，要提升为 KMP Gradle 模块。页面暂时保留在 `:shared`：这里承担 Kuikly `@Page` 注册、KSP 与 JS 动态包构建。先把**无页面注册的核心与组件**移出，避免在首轮模块化时同时承担路由/KSP/动态分包风险。

```text
:shared                         # App 装配层：@Page、路由、平台入口；最终依赖各 feature

:core:domain                    # 纯 Kotlin：业务模型、规则、格式化、协议，零 Kuikly View
:core:design                    # Theme、Token、字体缩放、颜色与 MotionSpec

:component:ui                   # GlassSurface、AppBar、ModalSheet、UndoBar、SourceStamp
:component:cards                # CardModel、Registry、Assembler、CardShell、通用卡片 renderer
:component:chart                # Chart model/calculator、坐标/手势纯算法、绘图基元
:component:richtext             # 实体识别、富文本、选择/拖拽数据契约

:feature:chat                   # 第二阶段：Chat state、coordinator、feature components
:feature:detail                 # 第二阶段：详情 state、业务板块与页面组件
:feature:market                 # 第二阶段：市场 / 自选 / 风险按边界继续拆分
```

依赖只能向下：

```text
:shared → :feature:* → :component:* → :core:*
                    └───────────────→ :core:*
```

禁止 `:component:*` 反向依赖 `:feature:*` 或 `:shared`。例如目前 `AppChrome` 混入 Chat 会话、行情岛、术语和图表，拆后只有 `GlassSurface`、`AppBar` 进入 `:component:ui`；`QuoteIsland`、`SessionDrawer` 留在 `:feature:chat`。`DetailTimelineChart` 在完成数据契约与回调抽象前留在详情 feature，不得为了“模块数”强行抽成通用图表库。

### 11.1 模块准入与迁移顺序

模块必须同时满足以下至少三项才准入：被两个以上 feature 使用、拥有独立单测价值、依赖面稳定、单文件超过 500 行且职责清晰、需要独立版本演进。一次性页面区块不是模块候选。

| 顺序 | 模块 | 首批迁移内容 | 风险控制 |
|---|---|---|---|
| M0 | `:core:domain` | `common` 纯函数、`protocol`、纯 data model、详情规则 | 不引入 Kuikly 依赖；先让单测在模块内运行 |
| M1 | `:core:design` | Theme、Glass token、图标数据、MotionSpec | 主题 observable 仍由 `BasePager` 持有，不移动页面响应式读取 |
| M2 | `:component:cards` | `cards/core`、`CardShell`、通用渲染壳 | 清除 cards 对 `page/components` 的反向 import，先迁 `SourceStamp` |
| M3 | `:component:richtext` | EntityRecognizer、EntityRichText、拖拽模型 | View 仅通过回调暴露事件，不得导航或写自选 |
| M4 | `:component:ui` | ModalSheet、GlassSurface、AppBar 基元 | 不含 Chat drawer/island 状态机 |
| M5 | `:component:chart` | ChartCalculator、坐标/命中测试、绘图基元 | 详情分时图最后接入；不得直接复用版本不匹配的 vendor ChartKit |
| M6 | `:feature:*` | Chat/Detail 的 state、coordinator、feature component | 只有组件模块编译、测试、双端验证稳定后开始 |

每个模块迁移的顺序固定为：先复制并让测试通过 → 调整调用方 → 删除旧文件 → 加依赖禁令。禁止在同一个提交中既改组件行为又改模块边界。

## 12. 多 Agent 执行编排

并行的单位是“无共享写入域的交付物”，不是“把一个大文件切成几段同时改”。尤其 `ChatPage.kt` 在完全迁出前只能有一个写入 owner；任何两个 Agent 都不得同时改它、`settings.gradle.kts`、版本目录或同一个 Gradle 构建文件。

所有 Agent 都应在独立 Git worktree/分支工作，分支以 `codex/` 开头；集成人只在每个任务通过检查后按依赖顺序合并。当前工作区已有未提交改动时，先由负责人确认基线或建立独立 worktree，不能把重构混入未知改动。

| 角色 | 可写入范围 | 交付物 | 不得触碰 |
|---|---|---|---|
| A0 架构集成人 | `settings.gradle.kts`、根构建、模块依赖、架构规则文档 | 模块骨架、依赖图、合并记录 | feature 行为与 `ChatPage` 业务逻辑 |
| A1 领域/卡片 Agent | `:core:domain`、`:component:cards` 及其测试 | 无 UI 反向依赖的卡片模块 | 页面、Bridge、主题实现 |
| A2 设计/UI Agent | `:core:design`、`:component:ui` 及视觉测试清单 | UI 基元和稳定 API | Chat Island/Drawer、业务数据源 |
| A3 图表/富文本 Agent | `:component:chart` 或 `:component:richtext`，一次只选一个 | 纯算法测试、回调契约、迁移说明 | StockDetailPage 行为改动 |
| A4 Chat 迁移 Agent | `ChatPage`、`:feature:chat`、其测试 | 一个完整纵向状态切片、单独 commit | 同时迁移两个高风险手势 |
| A5 QA/发布 Agent | 测试脚本、验证记录、发布说明；默认不改业务源码 | 平台构建结果、截图/手测矩阵、缺陷报告 | 为了通过测试修改业务逻辑 |

若只有四个并发位，推荐顺序是：A0 先完成模块骨架和约束；随后并行 A1、A2、A3；A4 在 A0 合并后独占 ChatPage；A5 只针对已合并 commit 验证。高风险 Drawer/Island 迁移期间，其余 Agent 不修改 `:feature:chat`。

### 12.1 Agent 任务卡模板

每张任务卡必须包含：目标模块与唯一 owner、允许改动的文件范围、禁止修改范围、输入接口、输出接口、测试命令、Android/H5 手测路径、回滚 commit 与风险说明。完成定义是“代码、单测、调用方编译、文档、验证证据”同时齐全，不是“文件已移动”。

交接消息至少包含：变更的状态所有者、尚存的 Timer/版本号、动画 driver、已验证的平台、未验证风险、提交 hash。若发现 R1–R6 新陷阱，先更新 `AGENTS.md` 或对应架构文档，再交接下一位 Agent。

## 13. 质量门禁与发布命令

以下命令在 Windows PowerShell、项目根目录执行。每个 Agent 的本地最低门禁是 common 单测与 JS 编译；改动 UI/路由时还必须构建 Android 与 H5。

### 13.1 开发与合并门禁

```powershell
# 共享逻辑、协议、状态机和 JS 编译
.\gradlew.bat :shared:testDebugUnitTest :shared:compileKotlinJs

# Android Debug APK
.\gradlew.bat :androidApp:assembleDebug

# H5 开发分发产物
.\gradlew.bat :shared:jsBrowserDevelopmentExecutableDistribution
```

人工验证至少覆盖：新会话欢迎入场、历史会话切换、流式回复、抽屉、卡片 Sheet、实体长按/拖拽、详情页分时 scrub、自选拖拽。触及某项才执行该项；触及 Drawer/Island 必须在 Android 真机走完整 phase，不能只看编译。

### 13.2 Android 与 H5 候选发布

```powershell
# 先得到可发布的 Android APK
.\gradlew.bat :androidApp:assembleRelease

# 先生成 shared 的 Kuikly Release JS 包
.\gradlew.bat :shared:packEntryJsAssetsRelease

# 再封装 H5 静态分发目录
.\gradlew.bat :h5App:publishLocalJSBundle
```

产物位置：

- Android：`androidApp/build/outputs/apk/release/`
- H5：`h5App/build/distributions/`，以其中的 `index.html` 为入口

`shared:publish` 会向 Maven 仓库发布；它不是常规 App 发布命令，只有在 Maven 地址、凭据、版本号和发布授权均已明确时才可执行。

### 13.3 iOS 与 OpenHarmony

iOS 发布只能在 macOS/Xcode 环境完成。先在 macOS 执行：

```bash
./gradlew :shared:podPublishReleaseXCFramework
cd iosApp && pod install
```

之后在 Xcode 对 `iosApp.xcworkspace` 用 Release 配置 Archive；签名、Team、Bundle ID 与导出选项必须由发布负责人确认，不能由重构 Agent 猜测。

OpenHarmony 当前不应作为“已绿的发布目标”宣称：已有工程审计指出 `build.ohos.gradle.kts` 的依赖与 `expect/actual` 配置尚不完整。先以独立修复任务让下列命令通过，并在 DevEco 完成签名后再发布：

```powershell
.\gradlew.bat -c settings.ohos.gradle.kts :shared:assemble
```

修复后再由 `ohosApp/runOhosApp.sh` 所定义的 DevEco/Hvigor 流程构建、签名、安装 HAP。不要把 Android/H5 通过等同于 OpenHarmony 可发布。

### 13.4 发布前最终 Gate

1. 从干净的候选 commit 执行 13.1 的三条命令；
2. 执行 Android 与 H5 Release 命令，并打开实际产物做冒烟；
3. 检查 Git diff，调试截图、log、dump、密钥和本地配置均不进入发布；
4. QA Agent 记录版本、commit、测试命令、设备/浏览器、未覆盖项与已知风险；
5. 仅在所有阻断项为零时打 tag 和交付。发生构建锁冲突时先停止相关 Gradle 进程并重试，不能通过删除未知 build 目录“碰运气”。
