# StockChat 项目级目标架构与演进蓝图

> 版本：v1.0 ｜ 日期：2026-09-10 ｜ 定位：项目级架构决策与迁移标准
>
> 本文扩展《37-项目架构重构最终实施方案》：37 定义首个 Chat 纵向试点；本文定义所有页面、共享能力与未来 KMP 模块化的共同终局。它不是一次性目录迁移任务，也不授权改变现有产品行为。

## 1. 架构结论

项目的正确方向是**功能纵切 + 功能内四层分离 + 少量稳定共享基座**，而不是把所有代码塞进 `common`、`utils` 或一个“万能组件库”。

```text
Page（装配、生命周期、平台 Effect）
   ├── Feature Component（纯渲染、回调上抛）
   └── Feature State（UiState / Intent / Coordinator / Effect）
                      └── Data / Domain Port（Repository、Store、规则）

Shared UI / Design / Platform 只作为稳定基座，不能反向依赖 Feature。
```

最终目的不是减少文件数量，而是让每个新增需求都能清楚回答：

1. UI 在哪个 `component`；
2. 交互意图由哪个 `Intent` 表达；
3. 状态、Timer 和版本号由哪个 `Coordinator` 所有；
4. 数据从哪个 `Repository` 或 `Store` 得到；
5. 路由、震动、媒体、录音等跨端能力由哪个 `Effect/Port` 执行；
6. 这项能力是否已经满足“共享组件”的准入条件。

已识别的边界问题：

- `MarketDependencies` 是有效的临时 composition root，但同时装配了过宽的行情、自选、术语、提醒、风险能力；未来应按 feature 暴露更小的 Facade/Port。
- `data` 内仍出现 `PagerKeyValueStorage` 等 Pager 细节；数据层只应认识 `KeyValueStorage` 等端口，Pager 适配应留在 platform/assembly。
- `cards/stock/MarketCardRenderers` 反向导入 `page/components/SourceStampLine`；共享卡片不能依赖页面组件。
- `composer` 与 `chat/composer` 并存，说明 feature 归属尚未完全统一；新代码必须优先收敛到 `feature/chat/composer/*` 的命名模型。
- 现有 `ArchitectureBoundariesTest` 已验证存储端口可测试，但尚未对源码 import 方向形成自动门禁。

这些不是“代码写得不好”的结论，而是项目从原型高速迭代进入可维护阶段后的正常债务。

## 3. 目标目录与依赖方向

第一阶段先在 `:shared` 内按包落地；只有边界稳定、测试独立且有复用价值的区域，才进入 Gradle 模块。目录名称使用 `feature`、`foundation`、`shared` 描述归属，禁止新增含义不明的 `common`、`helper`、`manager`。

```text
com.kuikly.stockchat/
  app/                              # Router、Feature 装配、页面入口
  foundation/
    design/                         # Theme、Token、MotionSpec、Icon contract
    platform/                       # Navigation/Storage/Haptic/Media/Voice Port
    lifecycle/                      # Page 可见性、TaskScope、Scheduler contract
    ui/                             # 无业务的 GlassSurface、ModalSheet、反馈基元

  shared/
    market/                         # Quote、Insight、News 的跨 feature 数据契约
    cards/                          # Card model、assembler、通用卡片壳
    chart/                          # 纯图表计算与可复用绘图基元
    richtext/                       # 实体识别、富文本与拖拽数据契约

  feature/
    chat/
      page/                         # ChatPage，仅装配与生命周期
      component/                    # ChatComposer、QuoteIsland、SessionDrawer
      state/                         # ChatUiState、Intent、Effect、Coordinator
      data/                          # ChatSessionRepository、feature 内持久化
      composer/{component,state}/
      welcome/{component,state,data}/
      sheet/state/
      scroll/state/
    detail/{page,component,state,data}/
    watchlist/{page,component,state,data}/
    market/{page,component,state,data}/
    risk/{page,component,state,data}/
    glossary/{page,component,state,data}/
```

依赖只允许向下：

```text
app / feature page
        ↓
feature component ───────────→ foundation design/ui
        ↓ callbacks
feature state ───────────────→ feature data / shared domain / foundation lifecycle
        ↓ effect
app platform adapter ────────→ Android / iOS / H5 bridge

shared/*、foundation/* 不能 import feature/* 或 page/*。
feature component 不能 import Repository、Store、Provider、Bridge 或 Pager。
```

页面可以引用 feature state 和 feature component；feature component 可以消费只读 RenderModel，但不得触发数据读取或生命周期决策。

## 4. 四层的精确职责

| 层 | 可以做什么 | 明确禁止 |
|---|---|---|
| `page` | 路由参数、页面生命周期、Feature 装配、执行 Effect、持有 ViewRef | 业务 Timer、网络解析、持久化读写、复杂手势状态字段 |
| `component` | Kuikly View、布局、样式、无障碍、将点击/手势转 Action | `acquireModule`、`setTimeout`、Repository/Store/Provider、跨组件状态裁决 |
| `state` | `UiState`、`Intent`、`Effect`、Reducer、Coordinator、版本守卫、任务取消 | 创建 Kuikly View、直接持有 Android/H5 Bridge 实现 |
| `data/shared domain` | 业务模型、Repository、缓存、持久化、解析、纯规则 | observable UI 状态、View、导航、Toast、Haptic |

### 4.1 标准交互流

```text
用户手势
  → Component.onAction(Action)
  → Page 转发 Intent
  → Coordinator / Reducer 更新 UiState 或发出 Effect
  → Page 执行 Haptic / Navigation / Media / Voice 等 Effect
  → 外部结果作为新的 Intent 回到 Coordinator
```

例如“选择媒体”不应让组件调用 Bridge；应是：

```text
MediaSheet Component → ChooseMediaSource(source)
MediaSheetCoordinator → OpenMediaPicker(source) Effect
Page → MediaPickerPort.open(source)
native result → MediaPicked(result) Intent
ComposerAttachmentCoordinator → 更新 attachments UiState
```

这保证 Android/H5 可以替换实现，测试可只使用 fake port，页面离开后的旧回调也有统一的版本守卫。

### 4.2 状态机模板

每个有异步时序、动画、手势或原生回调的 feature slice 使用以下命名，而不是笼统的 `Manager`：

```text
<Feature>UiState                 # 可渲染状态；必要时有 Kuikly/Plain state port
<Feature>Intent                  # 用户或外部输入
<Feature>Effect                  # Page/平台需要执行的副作用
<Feature>Reducer                 # 纯同步状态变化；可独立单测
<Feature>Coordinator             # Timer、Repository、版本号、lifecycle 编排
<Feature>Scheduler / TaskScope   # 可 fake 的调度与任务取消端口
```

不是每个静态页面都需要完整五件套：纯展示区块只需 `Component + RenderModel`；只有异步与交互复杂度达到阈值时才增加 Coordinator。

## 5. Kuikly 响应式与动效规则的架构化落地

现有 `AGENTS.md` 的 R1–R6 是硬规则，目标架构必须让它们更容易被遵守：

1. `UiState` 的 observable 只在 Component 的 `attr`、`event`、`vif`、`vfor`、`vbind` 闭包中读取；普通 builder 不读取可变状态。
2. 动效取值闭包由 feature component 接收，animation driver 在同一个 `attr` 内最后读取，`animate()` 是最后的状态相关调用。
3. `mounted → presented` 的两帧入场与 `version` 守卫必须由单一 Coordinator 所有；不允许组件自行启动 Timer。
4. Page 的 `pageDidDisappear/pageWillDestroy` 只调用 feature coordinator 的 `onDisappear/onDestroy`，统一取消任务、递增 revision。
5. 对每个 Coordinator 提供 fake scheduler 和 Plain state port，避免测试环境直接触发 Kuikly reactive observer。

建议在 `foundation/lifecycle` 孵化统一的 `FeatureTaskScope`：提供 `launch(delay)`, `cancelAll()`, `revision` 与 `isActive(revision)`。它必须先在两个以上 feature 稳定复用后才成为共享实现；目前各 Coordinator 的 scheduler port 保持可独立演进。

## 6. 共享组件孵化制度

共享不是“代码看起来像”，而是 API 已稳定的产品能力。一个组件只有同时满足下列至少三项才可从 `feature/*/component` 升入 `foundation/ui` 或 `shared/*`：

1. 已有两个以上 feature 的真实使用方；
2. Props、回调和状态边界已稳定；
3. 能独立写测试或视觉验收清单；
4. 不依赖某个 feature 的 Repository、导航、业务枚举或状态机；
5. 未来修改应由同一 owner 维护，而不是多个页面各自 fork。

### 6.1 当前候选与归属

| 候选 | 目标归属 | 现在是否可迁 | 原因 |
|---|---|---|---|
| `GlassSurface`、玻璃 token | `foundation/design` + `foundation/ui` | 是，先抽 API | 多页面已有稳定视觉语义 |
| `ModalSheet` / Sheet scrim | `foundation/ui/overlay` | 是，保留 state 在 feature | 壳可共用，CardSheet/MediaSheet 的状态机不可共用 |
| `SourceStampLine` | `foundation/ui/feedback` | 是 | 解除 cards 对 page/components 的反向依赖 |
| `CardShell`、CardModel/Registry | `shared/cards` | 是，维持业务卡扩展点 | 已跨聊天、详情、画廊使用 |
| `UndoBar`、Loading/Empty/Error | `foundation/ui/feedback` | 条件成熟后 | 先统一 Props 与无障碍文案 |
| `AppChrome` | 拆分后再定 | 否，不能整体上移 | 其中混有 Chat Drawer、QuoteIsland、术语和行情业务 |
| `DetailTimelineChart` / `RiskSkyChart` | 各自 feature | 暂否 | 交互、数据、动画契约尚不稳定 |
| `QuoteIsland`、`SessionDrawer`、`VoiceBar` | `feature/chat/component` | 否 | 仍依赖 Chat 状态和手势协议 |

共享组件 API 一律使用显式 `Props + Actions` 或具名参数；不得将 `BasePager`、整个 ViewModel、Repository 或 `Any` 传给组件。组件注释说明“适用场景、状态归属、无障碍与动画约束”，不重复描述每一行布局代码。

## 7. 数据、装配和跨端能力

### 7.1 数据访问

`Repository` 负责在线/缓存/离线降级的选择；`Store` 负责明确的本地持久化；`Provider` 只代表单一外部数据源。不要让 Page 决定在线、缓存与解析细节。

`MarketDependencies` 和 `ChatDependencies` 在当前阶段可继续作为 composition root，但演进目标是：

```text
app/assembly/
  AppFeatureGraph.forPager(pagerId)
    → ChatFeatureDependencies
    → DetailFeatureDependencies
    → WatchlistFeatureDependencies

foundation/platform/
  PagerStorageAdapter : KeyValueStorage
```

这样 `data` 只依赖 `KeyValueStorage`，不导入 Pager；Page 只获取本 feature 必需的依赖，而不是一整个市场服务桶。

### 7.2 跨端 Port 与 Effect

下列能力须定义在 `foundation/platform` 的 commonMain contract，由 Android/iOS/H5 适配：

- `NavigationPort`
- `StoragePort` / `KeyValueStorage`
- `HapticPort`、`ToastPort`
- `MediaPickerPort`
- `VoiceRecorderPort`
- `ClockPort`、`MotionPreferencePort`

现有 `BridgeModule` 是短期桥接实现；未来 Page 是唯一可接触它的 adapter。feature state 只能产生 Effect，不能 import `BridgeModule`。

## 8. 命名与注释规范

| 对象 | 标准命名 | 反例 |
|---|---|---|
| 页面 | `StockDetailPage` | `DetailScreenManager` |
| Feature 状态 | `StockDetailUiState` | `DetailData` |
| 纯事件 | `StockDetailIntent.SelectPeriod` | `onClickType` |
| 外部副作用 | `StockDetailEffect.OpenChat` | `doOpen` |
| 时序拥有者 | `DrawerGestureCoordinator` | `DrawerManager` |
| 纯规则 | `WatchlistReorderReducer`、`RiskCorrelationCalculator` | `CommonUtils` |
| 数据访问 | `QuoteRepository`、`ChatSessionStore` | `QuoteHelper` |
| 组件 | `DetailHeroSection`、`WatchlistRow` | `DetailView2` |

补充规则：

- Boolean 用 `is/has/can/should` 开头；进行态用 `isLoading/isPresented/isDragging`。
- 时间统一带单位：`delayMillis`、`exitDurationMs`、`startedAtMillis`；坐标带语义：`offsetX`、`pageY`。
- 版本守卫统一为 `revision` 或 `<feature>Revision`，不混用无含义 `version`。
- `State` 不叫 `Model`，除非它确实是不可变领域模型；UI 所需组合数据称 `RenderModel` 或 `UiState`。
- 注释优先说明“为什么”：平台陷阱、手势互斥、R4/R5 注册时序、业务不变量、降级原因。显而易见的 `setX`、布局和文案不写重复注释。

## 9. 分波迁移路线图

每波只做一个 feature 或一个共享能力；一个 commit 不同时改变行为、跨端 Bridge、模块边界与高风险手势。

### Wave 0：巩固已完成 Chat 试点

- 完成 Android/H5 welcome、流式贴底、CardSheet、媒体附件手测；记录设备与结果。
- 保持 Welcome 组件物理归档的独立提交；确认 `ChatWelcomeSection` 已不留重复实现。
- 为 Chat 遗留部分建立状态字段地图，不再向 `ChatPage` 新增无 owner 的 Timer/observable。

### Wave 1：Chat 的高风险状态机　✅ 已完成（2026-09-12）

1. `ComposerFocusCoordinator` + `VoiceSessionCoordinator`：焦点恢复、键盘、录音/转写、振幅和生命周期。
2. `DrawerGestureCoordinator`：边缘 pan、native fling、挂载/呈现、手势取消与卸载。 → ✅ `chat/drawer/state/`
3. `QuoteIslandCoordinator`：展开、投放、对比、详情 handoff、返回复位。 → ✅ `chat/island/state/`
4. `EntityInteractionCoordinator`：长按、拖拽、投放目标、二义实体与预览。 → ✅ `chat/entity/state/`

每项必须有 phase/revision 状态、fake scheduler 或 fake port 测试，且独立 Android/H5 手测。Drawer 与 Island 不并行改动。

**落地结果**：四项均按「StatePort + Coordinator + Scheduler + Effect」四件套落地；`ChatPage` 由 5,897 行降至 **5,273 行**；全量单测 **215 例通过、0 失败**（含各刀新增的 fake-scheduler 时序用例）。

**过程要点（供 Wave 2 复用）**：

- Island 抽取时引入过一次「功能链路全正常、只有样式不切换」的反应式回归——DSL 在 `attr {}` 内调用的查询（`isCompareLobbyVisible`）读了协调器内部**镜像字段**而非 StatePort observable，attr 不重跑。**规则：镜像字段只许协调器内部命令逻辑读；任何会被 DSL 在 attr 内调用的公开查询必须读 StatePort。** 已加守护用例并反向验证有效。
- 跨层反向依赖同步拆除：`SourceStampLine` 下沉为 `cards.components.CardSourceStampLine`（对应 §2 边界问题第 3 条，已闭环）；`AiChatMessage/AiMediaPart` 抽到 `data.provider.AiMessage`（评审 P1 的 Provider→chat 反向依赖，已闭环）。
- 迁字段前必须 grep 全部引用，**包括其他 coordinator 的 Effect 分支**：实体交互一刀即因 Island 遗留的 `ClearStockDrag/ClearTermDrag` 分支仍在写已迁走的字段，直到编译期才暴露。

### Wave 2：Stock Detail（第二个完整样板）

第 1 刀之后剩余三刀 + 收尾的可派发任务书，见 `docs/43-StockDetailPage-Wave2剩余纵切任务提示词集_v1.0.md`
（现状证据、边界、验收标准均已写好，可直接派给下一个执行方，无需重新读码）。

建议按以下顺序，而不是按视觉区块搬文件：

1. `DetailDataCoordinator`：Quote、Insight、News 的加载/缓存/降级与 loading/error RenderModel； → ✅ 第 1 刀已落地（2026-09-12）`detail/quote/state/`
2. `DetailChartInteractionCoordinator`：period、crosshair、scrub、圈选、气泡、prefill； → ✅ 第 2 刀已落地（2026-09-12）`detail/chart/state/`
3. `DetailAiInsightCoordinator`：AI 请求、流式文本、取消、reveal；
4. `DetailOverlayCoordinator`：新闻预览、披露 peek、互斥 overlay；
5. 最后把 Hero、Chart、Insight、News 归入 feature component。

### Wave 5：Gradle 模块化（最后进行）

只有 Wave 2–4 的包边界与依赖检查稳定后，才逐步引入：

```text
:core:domain      # 纯模型、规则、协议、格式化
:core:design      # Token、主题契约、MotionSpec
:shared:cards     # 卡片模型、注册与通用壳
:shared:richtext  # 实体与富文本契约
:shared:chart     # 可复用图表纯算法/基元
:feature:chat / :feature:detail / ...
:shared           # Kuikly @Page 注册、路由与最终装配
```

先模块化纯 Kotlin 或稳定共享组件，最后处理含 `@Page`、KSP、动态 JS 分包的页面。不要为展示“模块数”而在 feature 仍频繁变更时拆 Gradle。

## 10. 质量门禁与度量

### 10.1 每个迁移的完成定义

1. 有短规格：目标、范围、边界、不可变行为、验收；
2. 新状态只有一个 owner，Timer/任务有生命周期取消与 revision guard；
3. Coordinator 有纯状态或 fake scheduler/port 测试；
4. `:shared:testDebugUnitTest`、`:shared:compileKotlinJs` 通过；触及 UI 时补 Android/H5 手测；
5. `git diff --check` 通过，独立 commit 可回滚；
6. 迁移文档记录状态 owner、Effect、动画 driver、已验证平台和剩余风险。

### 10.2 自动化边界门禁

在 `buildSrc` 增加轻量 `verifyArchitectureBoundaries` 任务，按 package/import 扫描并失败于：

- `foundation/**` 或 `shared/**` import `feature/**`、`page/**`；
- `feature/**/component` import `data.provider`、`*Repository`、`*Store`、`BridgeModule`；
- `feature/**/data` import Kuikly View 或 Page；
- 新增 `Common`、`Helper`、`Manager`、`Utils` 类型名；
- 未在 allowlist 中的跨 feature import。

它先只报告 warning，连续两个迭代稳定后升级为 CI failure。该任务比要求开发者“自觉分层”可靠，也比一开始引入大型架构框架更适合当前项目。

### 10.3 观察指标

- 新功能涉及的文件数与跨 feature import 数；
- 每个 Page 直接 `setTimeout`、`acquireModule`、Provider 调用数量；
- 每个 Coordinator 的时序测试覆盖数；
- Android/H5 行为回归通过率；
- 共享组件的真实使用方数量与 API breaking change 数量。

“Page 行数”只作为信号，不作为 KPI。一个 800 行但包含五个无 owner Timer 的页面，风险可高于一个 1,500 行、边界明确的展示页面。

## 11. 给团队的执行原则

1. **先修边界，再谈模块。** 包结构和测试先稳定，Gradle 模块最后迁。
2. **先状态机，再搬 UI。** 动效、手势、原生回调先找到唯一 owner，组件归档才安全。
3. **共享以使用证明，不以设想证明。** 复用不到两处的组件留在 feature。
4. **复用契约，不复用 Page。** 组件只接收 Props/Actions；不能把整个 Page 或 ViewModel 下传。
5. **一条纵切一个提交。** 可独立验收、可独立回滚，避免“架构重构”吞掉产品迭代。
6. **注释记录不变量。** 重点写 R4/R5、平台差异、生命周期与手势互斥，帮助下一位开发者安全修改。
