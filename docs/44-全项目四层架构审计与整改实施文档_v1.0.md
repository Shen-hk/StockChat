# StockChat 全项目四层架构审计与整改实施文档

> 版本：v1.0  
> 审计日期：2026-09-12  
> 审计对象：当前 `master`，HEAD `fac42b1`  
> 目标：判断项目是否满足 Page / Component / Data / State 四层分离，并给出可直接派发的整改任务。  
> 边界：本文只做架构审计与实施设计，不授权改变产品功能、视觉、文案、动画参数、手势阈值或平台协议。

---

## 1. 一句话结论

**当前项目整体得分 64/100，属于“局部达到、全项目尚未达到四层分离验收线”。**

Chat 和 Detail 已经建立了可复制的 `StatePort + Coordinator + Scheduler + Effect + Component` 纵切范式，数据层也已有 Repository、Store、缓存降级和可注入存储端口；但 Market、Risk、Watchlist、Glossary 等核心页面仍把状态、时序、数据装配和大段 DSL 放在 Page 内，顶层 `page/components` 同时收纳通用组件和 Feature 私有组件，且跨层依赖目前只靠约定、没有自动门禁。

因此，本项目现在可以继续孵化通用组件，但**不能把“已经有 components 目录”视为已经形成通用组件库**。先完成归属校正与依赖门禁，再做 Gradle 模块化，风险最低。

建议将全项目验收线设为 **80/100**。完成本文 P0、P1 后预计可达到 82–86 分；P2 模块化不是达到四层分离的前置条件。

## 2. 审计方法与基线

本次按以下证据评分：

1. 包与文件结构；
2. Page 中 observable、Timer、revision/generation、Provider/Store/Repository 和 DSL 的实际分布；
3. Component 是否依赖 Page、数据源、Bridge 或自持跨帧时序；
4. State 是否有唯一所有者、可替换 Scheduler/Port、生命周期取消和单测；
5. Data 是否与 Pager、Kuikly View、页面生命周期解耦；
6. 共享组件是否有两个以上真实使用方、稳定 API 和正确依赖方向；
7. 构建与测试是否能阻止架构回退。

## 4. 四层逐层判断

## 4.1 Page 层：未全局达标

目标职责只能是：路由参数、生命周期转发、依赖装配、ViewRef、平台 Effect 执行和页面根布局。

当前正向证据：

- `ChatPage` 已将 Welcome、Drawer、Island、Entity、Composer、Voice、Message Action、Scroll、Card Sheet 等状态交给独立 Coordinator；
- `StockDetailPage` 已将 Quote/Insight/News、Chart、AI、Overlay 状态交给四个 Coordinator；
- 两页都已建立 `pageDidDisappear/pageWillDestroy → coordinator` 的生命周期转发模式。

当前不达标证据：

- `MarketPage` 仍持有 32 个 observable、多个 generation/revision、两套 AI Provider/Typewriter、新闻滚动时钟和 34 处 Timer 引用；
- `RiskMapPage` 仍持有行情数据、星图手势、AI 流、预警生成和持久化；
- `WatchlistPage` 同时持有列表数据、搜索、原因编辑、拖拽、Undo、简报和收件箱；
- `StockDetailPage` 虽已纵切四个状态域，仍保留顶部折叠、行情 ticker、收藏反馈、图表 draw/tape、公司区 tab、句图联动等 22 个页面 observable；
- `ChatPage` 仍有约 210 个函数，说明它尚未成为“薄装配层”；
- 全部 Page 合计仍有约 172 处 observable/list 声明和 124 处 `setTimeout` 文本引用。

结论：Page 层是当前最大扣分项。

## 4.2 Component 层：有能力，但目录与依赖未收口

正向证据：

- `chat/*/component` 已出现明确 Props/Actions 边界；
- `detail/page/component` 已有七个具名区块；
- `AppTopBar` 被十余页面使用，`CardShell` 被聊天、详情、画廊和卡片 renderer 使用；
- `GlassContainer/GlassRenderer`、Line Icons、FeatureTile 已具备共享基础。

不达标证据：

- `page/components/AppChrome.kt` 1,756 行，同时包含 ChatTopNav、QuoteIsland、ChatDrawer、AppTopBar 和 DataModeBadge，通用与 Chat 私有内容混在一个文件；
- `detail/page/component/*` 大量反向 import `com.kuikly.stockchat.page.*` 和 `page.components.*`，组件并未真正从 Page 脱离；
- `chat/*/component` 仍反向复用 `page.components` 中的图标、VoiceBar、ComparePanel 等，Feature 归属没有闭合；
- 非 Page 包反向 import `com.kuikly.stockchat.page...` 的当前命中约 66 处；
- `DetailTimelineChart`、`RiskSkyChart`、`DetailBoardBlocks` 等组件内部仍直接启动 Timer；`DetailTimelineChart` 还自持多项 observable 交互状态；
- `SourceStampLine` 存在两套入口：`cards/components/CardSourceStampLine` 与 `page/components/SourceStampLine`，容易继续分叉；
- `UndoBar`、`SegmentBar` 当前各只有一个真实业务使用方，不应仅因位于 `components` 就判定为成熟共享组件。

结论：项目已经能做组件，但还没有形成可靠的“通用组件治理”。

## 4.3 State 层：Chat/Detail 达标度高，其余页面缺失

正向证据：

- 多数 Chat/Detail Coordinator 都有 Fake State/Scheduler/Port 单测；
- 状态、Effect 和平台副作用之间已有清晰转发；
- 复杂动画与手势已开始由唯一 Coordinator 管理，并考虑 Kuikly R1–R5；
- Coordinator 测试覆盖量较高，是后续迁移最值得复制的资产。

不达标证据：

- State 方案尚未推广到 Market、Risk、Watchlist、Glossary、Alert；
- 多个 Component 仍自持 Timer/observable，使状态所有权不唯一；
- 部分 State 仍 import `page.detail.DetailOverlay`、`page.components.ChartFlag`、`page.detail.AnchorIndex`，形成 `state → page` 反向依赖；
- State 实现大量使用已弃用的无 PagerScope `observable(...)` API，虽不影响本轮功能，但增加未来 Kuikly 升级风险。

结论：State 层的“方法”已经验证，缺的是全项目推广和边界清理。

## 4.4 Data 层：基础较好，但基础设施混入业务包

正向证据：

- `QuoteRepository` 已承担在线/缓存/离线降级；
- Store 多数支持注入 `KeyValueStorage`，可在单测中脱离 Pager；
- `PlatformHttpClient` 已存在 expect/actual 跨端端口；
- Provider、Repository、Store 的角色大体可辨认。

不达标证据：

- `MarketDependencies` 位于 `data`，实际却是 App composition root；
- `ChatDependencies.forPager` 与 `MarketDependencies.forPager` 在业务包内直接创建 Pager 适配器和具体 Provider；
- `PagerKeyValueStorage` 位于 `data/storage` 并依赖 `PagerScope/SharedPreferencesModule`，应属于 platform adapter；
- 多个 Store 保留 `constructor(pagerId)`，使纯数据层可以绕过注入端口；
- `TencentQuoteProvider`、`EastMoneyInsightProvider`、部分 `AiProvider` 实现直接依赖 `PagerScope` 与 Kuikly module；
- `data/Appearance.kt` import Kuikly 的 `TextAttr/InputAttr/TextAreaAttr`，它是 Design/UI 基础设施，不是 Data；
- Provider 包同时承载 Quote、News、Disclosure、SourceStamp 等可渲染模型，数据契约与外部数据源实现尚未分包。

结论：数据能力强于目录表达；需把“业务数据”与“平台适配/装配”物理分开。

## 4.5 Android / iOS / H5 / Ohos 宿主层：边界位置正确，Bridge 内部偏大

四端宿主总体承担渲染入口、Router、媒体、语音、分享和触感，位置上属于 Platform Adapter，没有发现宿主 UI 反向承载 commonMain 业务页面的情况，这是正确方向。

主要风险是 Bridge 单文件过大：Android `KRBridgeModule.kt` 约 1,061 行、iOS `HRBridgeModule.m` 约 852 行、Ohos `KRBridgeModule.ets` 约 594 行。它们把 method dispatch、参数解析、媒体文件处理、语音会话、分享/截图等多种能力放在一起。H5 Bridge 较小，但与原生端依赖同一组字符串方法名，缺少一份 common contract 自动约束四端一致性。

宿主层不计入 Page/Component/Data/State 四层本体，但它直接影响 Effect adapter 是否可维护。整改方向是保留一个薄 `KR/HRBridgeModule` 作为协议入口，内部按 capability 分给 Navigation、Media、Voice、Share、Haptic service；方法名和 JSON payload 在 commonMain 定义常量/模型，四端做契约测试，不能各端自行复制字符串。

## 5. 目标架构与强制依赖方向

第一阶段仍保留单一 `:shared` Gradle 模块，只做包边界；不要在业务状态迁移同时拆 Gradle 模块。

```text
com.kuikly.stockchat/
  app/
    page/                         # @Page 入口，可最后迁；只装配
    assembly/                     # AppFeatureGraph、各 FeatureDependencies 工厂
    platform/                     # PagerStorage/Navigation/Haptic/Media/Voice 适配器

  foundation/
    design/                       # Theme、TypeToken、MotionSpec、语义化 Icon
    lifecycle/                    # Scheduler、TaskScope、revision/cancel contract
    ui/
      chrome/                     # AppTopBar、DataModeBadge
      surface/                    # GlassSurface
      overlay/                    # 仅通用壳，不含业务状态机
      feedback/                   # Loading/Empty/Error/SourceStamp

  shared/
    market/model/                 # Quote、News、Disclosure、SourceStamp 等只读契约
    cards/                        # Card model/registry/assembler/shell
    chart/                        # 纯计算、viewport model、无 Feature 状态
    richtext/                     # 识别、Span、拖放契约

  feature/
    chat/{page,component,state,data}/
    detail/{page,component,state,data}/
    market/{page,component,state,data}/
    watchlist/{page,component,state,data}/
    risk/{page,component,state,data}/
    glossary/{page,component,state,data}/
    alert/{page,component,state,data}/
```

考虑当前代码已经使用 `com.kuikly.stockchat.chat` 和 `...detail`，实施时可先保留这两个根包，新增 Market/Risk 等同级 Feature 包。待依赖门禁稳定后，再做一次纯机械 `chat → feature.chat` 命名迁移。不要把包改名与状态机迁移放在同一提交。

强制依赖方向：

```text
App Page / Assembly
       ↓
Feature Component  →  Foundation UI / Design
       ↓ Action callback
Feature State      →  Feature Data / Shared Model / Foundation Lifecycle
       ↓ Effect
App Platform Adapter

Shared / Foundation 禁止依赖 Feature 或 Page
State 禁止依赖 Page、View、具体 Bridge
Component 禁止依赖 Repository、Store、Provider、Bridge、Pager、Timer
Data 禁止依赖 View、observable UI State、Navigation、Toast
```

### 5.1 四层完成定义

| 层 | 完成标准 |
|---|---|
| Page | 只保留 `body` 根装配、生命周期、ViewRef、依赖注入和 Effect adapter；没有业务 Timer/revision/Provider 决策 |
| Component | API 是 Props/Actions 或具名 state accessor/callback；无数据源、Bridge、跨帧时序；observable 只在合法 reactive closure 内读 |
| State | 一个交互域只有一个 Coordinator；有 UiState、Intent/公开方法、Effect、可 fake Scheduler/Port；销毁后旧回调 no-op |
| Data | Repository 决定在线/缓存/离线；Store 只负责本地持久化；Provider 只负责单一外部源；均通过端口注入 |

## 6. 通用组件孵化结论

### 6.1 可立即确认为共享基座

| 当前文件/能力 | 目标位置 | 修改方式 |
|---|---|---|
| `page/components/AppChrome.kt` 中的 `AppTopBar`、`AppTopBarAction`、`AppTopBarMetric` | `foundation/ui/chrome/AppTopBar.kt` | 连同私有纯 UI helper 移出；API 只保留 Props/Actions |
| `DataModeBadge` | `foundation/ui/feedback/DataModeBadge.kt` | 不依赖 Page 或数据源，只接收展示文案/色调 |
| `glass/GlassContainer.kt`、`GlassRenderer.kt` | `foundation/ui/surface` + `foundation/design` | Renderer/tuning/token 与 View wrapper 分开 |
| `cards/components/CardShell.kt` | `shared/cards/component` | 保留 CardContext/Events；不得反向 import Feature |
| 两套 SourceStampLine | `foundation/ui/feedback/SourceStampLine.kt` | 合并为一个 API；Card 与 Insight 都调用它 |
| `page/components/LineIcons.kt` | `foundation/ui/icon` | 以语义名公开；底层 path helper 保持 private |

### 6.2 满足条件后再晋升

| 候选 | 当前处理 |
|---|---|
| `FeatureTile` | 先留 foundation 候选区；统一三处以上调用的 padding、title/subtitle/action/accessibility 后再冻结 API |
| `UndoBar` | 目前主要服务 Watchlist，先迁 `watchlist/component`；第二个真实使用方出现后再上移 |
| `SegmentBar` | 目前主要服务 Glossary，留 `glossary/component` |
| `NewsMarquee/NewsTape` | 先定义 `NewsTapeProps` 与外部 offset/paused Action；Market 与 Detail 均稳定复用后再上移 |
| Loading/Empty/Error | 先盘点现有页面文案和尺寸，形成统一 Props；禁止把业务空态文案写死在共享组件 |

### 6.3 明确不能作为通用组件整体迁移

- `AppChrome.kt` 整体：其中 QuoteIsland、ChatDrawer 是 Chat Feature；
- `DetailTimelineChart`：数据、手势、Timer、气泡和 Detail 状态仍耦合；
- `RiskSkyChart`：属于 Risk Feature；
- `ChatMessageComponents`、VoiceBar、ComparePanel：属于 Chat Feature；
- `DetailBoardBlocks`：属于 Detail Feature，只有纯数学模型可进入 shared/chart/domain。

共享组件晋升必须同时满足至少三项：两个以上真实 Feature 使用方、Props/Actions 稳定、无 Feature import、可独立测试/视觉验收、同一 owner 维护。禁止以“可能未来复用”为理由提前上移。

## 7. 整改工作包（可直接派发）

以下顺序按依赖关系排列。同一个大 Page 文件同一时刻只能有一个写入 owner；每个工作包独立提交、可独立回滚。

## P0-A：建立自动架构门禁

### 修改位置

- 新增 `scripts/check_architecture.sh`；
- 在根 `build.gradle.kts` 或 `shared/build.gradle.kts` 注册 `architectureCheck`，调用该脚本；
- 新增 `docs/architecture/package-rules.md`，把本文第 5 节规则固化为短规则；
- CI 若以后建立，必须执行 `architectureCheck`。

### 怎么改

脚本扫描 `shared/src/commonMain/kotlin` 的 package/import，第一阶段对既有债务使用 allowlist 文件，新增违规直接失败。规则至少包含：

1. `data` 不得 import `page`、Kuikly views/reactive、Navigation/Toast；
2. `component` 不得 import Repository/Store/Provider、Bridge、SharedPreferences、PagerScope；
3. `state` 不得 import `page`、Kuikly View、具体平台实现；
4. `shared`、`foundation` 不得 import `chat/detail/market/...` Feature；
5. Page 新增 `setTimeout`、Provider 构造、业务 `by observable` 时失败；
6. `page/components` 禁止新增文件，只允许逐步搬出。

Allowlist 必须逐条记录“文件 + 原因 + 删除它的工作包”，不得只按整目录豁免。每个后续工作包必须减少 allowlist 数量。

### 验收

- 当前基线能通过；
- 人工加入一条禁止 import 时任务失败；
- 删除测试违规后恢复通过；
- `architectureCheck` 小于 5 秒，便于每次提交运行。

## P0-B：移动装配根和平台适配器

### 修改位置

- `data/MarketDependencies.kt` → `app/assembly/MarketFeatureGraph.kt`；
- `chat/ChatDependencies.kt` 的 `forPager` 工厂 → `app/assembly/ChatFeatureGraph.kt`；
- `data/storage/PagerKeyValueStorage` → `app/platform/KuiklyKeyValueStorage.kt`；
- 新建更小的 `ChatFeatureDependencies`、`DetailFeatureDependencies`、`MarketFeatureDependencies` 等接口/数据类；
- `data/Appearance.kt` 拆到 `foundation/design/Appearance.kt` 与 `foundation/ui/FontScaleAttr.kt`。

### 怎么改

1. Store/Repository 构造器只接收 Port；逐步弃用并最终删除 `constructor(pagerId)`；
2. `forPager` 只能出现在 App Assembly，Feature/Data 内不能自行获取 Pager；
3. Page 从 App graph 取本 Feature 最小依赖集，不能获取包含九个服务的万能 `MarketDependencies`；
4. `TencentQuoteProvider`、`EastMoneyInsightProvider`、OpenAI Provider 分批改为注入 `PlatformHttpClient`、Clock、Storage，不直接 `acquireModule`；
5. 本工作包只改装配，不改 Provider 解析与降级逻辑。

### 验收

- Data 层不再 import `PagerScope`、`SharedPreferencesModule`；
- 所有 Store 单测继续使用 `InMemoryKeyValueStorage`；
- Provider parser 既有测试全过；
- Android/JS 编译通过。

## P0-C：纠正共享 UI 与 Feature 组件归属

### 修改位置

- 拆 `page/components/AppChrome.kt`：
  - `AppTopBar`/`DataModeBadge` → `foundation/ui`；
  - `ChatTopNav`/StockIsland/CompareIsland → `chat/island/component/QuoteIsland.kt`；
  - `ChatDrawer` → `chat/drawer/component/ChatDrawer.kt`；
- `ChatMessageComponents.kt`、`ChatScaffolding.kt`、`VoiceBar.kt` → `chat/.../component`；

## 8. 每个执行任务的固定模板

交给开发人员时，每张任务卡必须包含：

### 目标

明确唯一状态所有者，Page 仅装配，Component 仅渲染，Data 仅提供数据。

### 范围

列出迁移字段、函数、Timer、Provider/Store 调用和 DSL 函数；先 grep 全部读写点。

### 不做

不改视觉、文案、动画数值、手势阈值、路由、Prompt、降级策略；不与包改名、依赖升级或新功能混在同一提交。

### 实现要求

1. StatePort 有 Kuikly observable 实现和 Plain/Fake 测试实现；
2. Scheduler/Clock/Repository/Bridge 通过接口注入；
3. Coordinator 是 Timer/revision/generation 的唯一 owner；
4. 平台行为发 Effect，由 Page adapter 执行，结果再作为 Intent 回来；
5. Component 用 Props/Actions，不得接收 Page、Repository、Store 或 Provider；
6. 严格遵守 AGENTS.md R1–R8。

### 自动验收

```text
./gradlew architectureCheck
./gradlew :shared:testDebugUnitTest
./gradlew :shared:compileDebugKotlinAndroid
./gradlew :shared:compileKotlinJs
git diff --check
```

涉及 Ohos common/actual 时，额外按 AGENTS R8 执行：

```text
./gradlew -c settings.ohos.gradle.kts :shared:linkDebugSharedOhosArm64
```

### 人工验收

每个状态域必须列出正常、快速重复、离页回调、退后台、reduce motion、Android/H5；与 native bridge 有关时再补 iOS/Ohos。

### 提交要求

- 一个状态域一个 commit；
- 提交前列出 `git diff --cached --stat`；
- 不得夹带其他会话 WIP；
- 大 Page 同一时刻只有一个写入 owner；
- 提交说明包含变更文件、职责变化、测试证据、未覆盖风险。

## 10. 推荐排期与人员安排

| 阶段 | 工作包 | 建议人日 | 可并行条件 |
|---|---|---:|---|
| 第 0 阶段 | P0-A 门禁 | 1 | 可单独进行，不改业务大页 |
| 第 0 阶段 | P0-B 装配/平台 | 2–3 | 与大页迁移前半段避免同改 import 区 |

| 第 1 阶段 | Chat 收口 | 4–6 | `ChatPage.kt` 只允许一个 owner |
| 第 1 阶段 | Detail 收口 | 4–6 | 可与 Chat 并行；`StockDetailPage.kt` 单 owner |
| 第 1 阶段 | Market | 4–5 | 独立 Page，可并行 |
| 第 1 阶段 | Risk | 5–7 | 独立 Page，可并行 |
